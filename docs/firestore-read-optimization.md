# Firestore 讀取量研究與優化

日期：2026-11-14（台灣時間）；第七節 2026-11-15 更新
範圍：找出網站所有會產生 Firestore 讀取的地方，估算各自的占比，提出優化方案，並記錄本次已實作的改動。
相關文件：[公告讀取量優化紀錄](announcement-read-optimization.md)

> 名詞：「冷啟動」指瀏覽器從零開始載入網站，包括重新整理、開新分頁、主畫面 App 重開、從 Google/LINE/Threads 點進來。Firestore 計費以「文件讀取次數」計算，Spark 免費方案每天 50,000 次。

---

## 一、結論摘要

1. **今天超標的主因是公告已讀統計的重試風暴，不是使用人數。**
   - 1d207cb8 的網站在 11/13 17:03 上線，但它需要的 Firestore 規則到 11/14 04:19 才發布。
   - 這 11 小時內，每個開著、且有「待送出回條」的分頁都會一再重跑被拒絕的交易，每次 4–6 次讀取，沒有退避。觸發時機有三種：每 30 秒、每次切回分頁、其他分頁每次寫入 localStorage（作答時每題都會寫）。
   - 估計多出 1–4 萬次讀取。規則發布後已停止。
2. **平常每天 2–4.5 萬次的基準量，主要來自「冷啟動」的重複下載，跟人數關係不大：**
   - 已登入的使用者每次冷啟動都會下載**全部**作答紀錄與筆記。作答紀錄每做一次每日抽題就多一筆，所以成本每天都在增加。分頁在背景超過 30 分鐘再回來，監聽也會整批重讀。
   - 歷屆試題每看一題就重讀一次該題投稿，即使整份試卷的投稿已經讀過。每則投稿還多開回覆、按讚監聽，連只顯示題目的「題目」分頁也開。
   - 搜尋引擎爬蟲會逐一渲染 sitemap 裡的 3,672 個題目網址，每次都從零開始讀取。公告期間，每次渲染還會寫一筆假的「已送達」。
   - 每日抽題每答一題開一個詳解監聽，大多是「沒有投稿也要收 1 次」的最低收費。
3. **本次已實作 5 項優化**（第七節），目前還沒有 commit。其中作答紀錄的同步新增了一份雲端刪除紀錄，**要先發布 Firestore 規則，再部署網站**（見 7.8）：
   - 公告重試防爆；
   - 爬蟲不連 Firestore；
   - 量測開關；
   - 歷屆試題的投稿改從整卷資料取得，回覆、按讚只在「討論區」分頁讀取；
   - 作答紀錄與筆記改為增量同步，只讀上次之後的變動；跨裝置刪除改由雲端的刪除紀錄同步。
4. **需要你決定的事**列在第九節，包括：要不要升級 Blaze（同樣每天 5 萬次免費，超過才收費）、公告統計要不要改用 GA4、公告要不要改成不需即時監聽的發送方式。

## 二、今天為什麼超標（時間線）

Firebase 用量圖以美國太平洋時間切日，所以圖上的「11/13」是台灣時間 11/13 16:00 到 11/14 16:00。

| 時間（台灣）              | 事件                                                                                                                                                                                |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 11/12 19:13               | dea4762b（公告功能）commit。網站當晚上線，但公告用的規則到 11/13 09:39 才發布。在那之前，每個分頁的公告監聽都被拒絕，被拒後每 30 秒重訂閱一次。被拒絕的查詢是否計費，官方沒有說明。 |
| 11/13 09:39               | dea4762b 規則發布。之後每次已讀統計都直接更新公告文件，所以每更新一次，所有正在監聽公告的分頁各被收 1 次讀取（扇出）。                                                              |
| 11/13 15:25               | 1d207cb8 把統計移到 `pushMessages/{id}/stats/{stage}`，避免扇出。                                                                                                                   |
| 11/13 17:03               | 1d207cb8 網站上線（Vercel 部署時間 09:03:47Z），規則還沒發布。統計交易讀 `stats` 時被拒，回條一直停在「待送出」。                                                                   |
| 11/13 17:03 – 11/14 04:19 | **重試風暴**，詳見下方說明。                                                                                                                                                        |
| 11/14 04:19               | 規則發布（Rules 歷程「Today • 4:19 AM」）。04:38 與 04:46 兩次對 `stats/live` 的無驗證 GET 都回 404（只有新規則允許讀這個路徑），確認已生效。                                       |

**重試風暴怎麼發生的：**

- 每個卡住的回條，每次 flush 都會跑 2 次交易：第 2 次是程式刻意對 permission-denied 的重試。
- 每次交易讀公告文件與回條文件各 1 次，再加上被拒的 stats（是否計費不明）；兩次交易合計約 4–6 次讀取、0 次寫入。
- flush 的觸發時機：每 30 秒、分頁切換可見性、恢復連線，以及**任何** localStorage 變動。其他分頁每答一題都會寫 localStorage。
- 結果：一個前景分頁每小時約 480–720 次讀取，多開分頁就會疊加。

整段時間估計多出**約 1–4 萬次讀取**，疊在 2–4.5 萬的基準上就超過 5 萬。不確定的地方有兩個：被拒絕的讀取是否計費（官方沒寫），以及當時開著多少分頁。

同一天還有兩個無法量測的加成：

- **Firebase Console 的資料檢視器**本身就是即時監聽，開著 pushMessages、receipts、users 等集合時，讀取算進同一個額度，用量圖上分不出來。
- **爬蟲渲染**在公告期間每次都會用新的瀏覽器編號建立回條，約 7 讀 + 2 寫。

## 三、Firestore 計費重點（已查證）

查證來源包括官方文件與 `node_modules/@firebase/firestore`（SDK 4.17.0，隨 firebase 12.17.1）的原始碼，詳細出處見附錄。

| 項目                          | 規則                                                                                                                                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最低收費                      | 每個查詢或監聽至少收 1 次，**沒有結果也收**。這類最低收費**不會顯示**在用量圖上，所以實際用量比圖上多。                                                                                                       |
| 監聽開始時                    | 結果集裡每份文件收 1 次。                                                                                                                                                                                     |
| 監聽期間                      | 每份新增或變更的文件收 1 次，包括自己寫入後傳回來的回音。刪除不收費。                                                                                                                                         |
| 斷線超過 30 分鐘              | 重新連上時當作全新查詢，整批重讀。                                                                                                                                                                            |
| 預設快取                      | `getFirestore()` 預設是記憶體 LRU 快取。同一分頁內重新監聽同一個查詢，會帶 resume token、只拿變動（30 分鐘內）。但**冷啟動一律從零開始**，查詢條件裡若有 `Timestamp.now()` 等每次都不同的值，也一樣從零開始。 |
| `getDocs` / `getDoc`          | SDK 內部是「監聽一次就取消」，計費跟監聽相同。之後再對同一查詢開監聽，同分頁內可以接續上一次的結果。                                                                                                          |
| 規則裡的 `get()` / `exists()` | 每讀一份文件收 1 次，**請求被拒絕也照收**。                                                                                                                                                                   |
| 交易                          | 每個 `transaction.get` 收 1 次。只讀不寫的文件，commit 時還會多收 1 次驗證讀取。permission-denied 時 SDK 不會自動重試。                                                                                       |
| `count()`                     | 每 1,000 筆索引項收 1 次，最少 1 次。                                                                                                                                                                         |
| 用 `source: 'cache'` 監聽     | 只看本機快取，不建立伺服器查詢，不收費。其他監聽讀進來的文件也會即時反映到這個監聽。                                                                                                                          |
| Spark 額度                    | 每天 5 萬次讀取，太平洋時間午夜重置（台灣 16:00）。超過後請求會收到 RESOURCE_EXHAUSTED。                                                                                                                      |
| Blaze                         | 免費額度相同，超過的部分才收費：asia-east1 每 10 萬次讀取 US$0.0345，us-central1 US$0.03。預算警示只寄信，**不會**自動停止 Firestore。                                                                        |

**已排除的來源：**

- 建置與伺服器渲染都不讀 Firestore：題目頁的資料來自本機檔案，sitemap 是靜態檔。
- 本機開發與 e2e 測試沒有 Firebase 設定（沒有 `.env.local`），不會讀正式資料庫。

**會讓讀取一直變多的資料：**

- 投稿從不真的刪除。軟刪除與被取代的詳解仍留在資料庫，每次查詢都會一起讀到，只是畫面上不顯示。
- 回覆和按讚是整批讀進來再數。
- 作答紀錄、筆記、未完成進度只增不減。

**多分頁：** 每個分頁各自有一份 Firestore 連線、快取與全部監聽，所以每個分頁的成本都會乘上分頁數。

## 七、本次已實作的優化

共 5 項，2026-11-14 實作，11-15 修訂了 7.1、7.4、7.5。目前還沒有 commit。

7.5 新增了一份雲端刪除紀錄，**要先部署 Firestore 規則**（`firebase deploy --only firestore:rules --project shaneweb`），確認發布後再部署網站，見 7.8。其他幾項不需要規則或索引。

### 7.1 公告：回條重試不會再失控（防止今天的事件重演）

檔案：`src/components/push-messages.tsx`、`src/lib/push-messages.ts`、`src/lib/push-messages-firestore.ts`、`src/lib/listen-retry.ts`、`src/components/progress-sync-bridge.tsx`、`PUSH_MESSAGES.md`

改法：

- 每則回條在本機記錄連續失敗次數和下次可以重試的時間，**時間未到就不碰 Firestore**：
  - 網路問題、交易衝突等暫時性錯誤：從 1 分鐘起，每次加倍，最長 1 小時。
  - 重試也解決不了的錯誤（permission-denied、unauthenticated、invalid-argument、not-found）：從 1 小時起，每次加倍，最長 24 小時。
  - 送出成功就清除這些紀錄。
- 瀏覽器離線時不嘗試送出：試了只會失敗，還會拉長等待。
- 恢復連線時：
  - 因為斷線或逾時（unavailable、deadline-exceeded，或沒有錯誤代碼）而在等待的回條，馬上重試。失敗次數保留，再失敗就接著加倍。
  - 其他原因的等待要等完：規則拒絕、多位訪客同時更新統計造成的衝突（aborted、failed-precondition）、當日額度用完（resource-exhausted）。很多分頁同時恢復連線時，才不會一起重試這些。
- 其他分頁寫入 localStorage（每答一題都會寫）不再觸發送出。只有公告相關的 key 變動才會更新畫面，例如別的分頁按了已讀，這裡的提示也會關掉。
- 同一個瀏覽器開多個分頁時，用 Web Locks 確保一次只有一個分頁在送出。瀏覽器拒絕 Web Locks 時（例如沙盒框架、封鎖網站資料），這個分頁就不加鎖直接送出。
- 公告監聽失敗後的重新訂閱，改成從 30 秒起每次加倍，最長 30 分鐘，伺服器正常回應後才歸零。
- 公告監聽遇到重試也解決不了的錯誤（缺索引、規則還沒部署等），就不再重新訂閱，等瀏覽器恢復連線或重新載入頁面。這套判斷放在 `src/lib/listen-retry.ts`，作答進度的監聽（`progress-sync-bridge.tsx`）也共用。
- 恢復連線時，只有監聽處於失敗狀態才重新訂閱。正常的監聽 SDK 會自己重連，多訂閱一次就是整批重讀。
- 保留不變：交易本身；遇到 permission-denied 時再試一次（不同訪客共用同一份 stats 文件，會互相競爭）；畫面、已讀、測試模式、GA 事件。

效果：同樣是「規則晚發布」的情況，每個卡住的回條原本每 30 秒讀 4–6 次，現在是 1、2、4、8 小時才試一次，一天大約 5 次。公告監聽被拒後也不再每 30 秒重新訂閱一次。

你會看到的差異：

- 送出失敗時，統計數字會晚一點才計入。
- 若網站比規則或索引先上線，當時已開著的頁面收不到公告，要重新整理（或斷線後再連上）才會開始接收。之後新開的頁面不受影響。

### 7.2 爬蟲不連 Firestore

檔案：`src/lib/firebase-client.ts`

改法：

- 瀏覽器的 User-Agent 屬於已知爬蟲時，`getFirebaseServices()` 回傳 null，Auth、Firestore、Storage 都不啟動。
- 比對 44 個爬蟲關鍵字（Googlebot、Google-InspectionTool、GoogleOther、bingbot、Applebot、GPTBot、ClaudeBot、facebookexternalhit 等），以及 UA 裡帶「+http」說明網址的寫法。
- 刻意不擋的對象：HeadlessChrome（你自己的 Playwright 檢查）、LINE／Facebook／Instagram／Threads 的內建瀏覽器、搜狗手機瀏覽器、型號名稱含「bot」的手機（例如 CUBOT）。
- 測試涵蓋 50 個爬蟲 UA 和 17 個一般使用者 UA。
- 伺服器端和 `firebaseConfigurationAvailable()` 都沒有改，所以預先產生的頁面和 hydration 不受影響。

效果：爬蟲渲染的讀取歸零，也不會再產生假的「已送達」人次。

SEO 影響：爬蟲看到的頁面少了「討論區」分頁上的投稿數字。投稿內容本來就要按「看解答」或切到討論區才會出現，不在預設畫面裡。

限制：這是關鍵字比對，沒列到的爬蟲，或偽裝成一般瀏覽器的爬蟲，仍會照舊讀取。

### 7.3 量測開關 `?fsdebug=1`

檔案：`src/lib/firebase-client.ts`

- 網址加上 `?fsdebug=1` 後，這個分頁會在瀏覽器主控台印出 Firestore 的除錯紀錄：每個監聽要求、是否帶 resume token、收到哪些文件。
- `?fsdebug=0` 關閉，預設是關閉的。
- 用來實測第六節列的未知數，也用來確認本次改動的效果。

### 7.4 歷屆試題：投稿改讀整卷資料，回覆與按讚只在討論區讀

檔案：`src/lib/shared-discussions.ts`、`src/features/exams/exams-page.tsx`、`src/lib/firebase-client.ts`

改法：

- 題目頁本來就有一個監聽在讀「整份試卷的所有投稿」，用來顯示題號上的圓點。現在這一題的投稿直接取自這個監聽讀到的資料（`usePaperDiscussions`），這一題自己不開任何監聽，也不另外向伺服器查詢。
- 回覆、按讚、檢舉的監聽，等打開「討論區」分頁才建立。打開過之後切回「題目」仍保留，換到別題才關閉。
- 編輯投稿文字時，該題的回覆、按讚監聽不會再全部重建。
- 要等整卷資料由伺服器回應後，才會顯示「目前尚無詳解。」，避免先閃一下錯誤的空狀態。手上的資料已經有這一題的投稿時，就直接顯示。瀏覽器回報離線時馬上改用手上的資料，沒有回報離線則最多等 10 秒（跟 SDK 判定離線的時間一樣）。
- 換到另一份試卷（包括從試卷總覽回來）時重新等待，不會沿用上一份試卷的回應或錯誤。
- 伺服器的回應若只是確認手上的資料沒變，畫面不會重畫。
- 判斷「這台裝置會不會啟動 Firebase」改用只看設定與 User-Agent 的 `firebaseRunsHere()`，畫面繪製時不會順手啟動 Firebase。被擋掉的爬蟲因此也不會一直停在「正在載入詳解…」或「正在載入共享投稿…」。
- 整卷資料讀取失敗時，討論區會顯示錯誤訊息。以前這是由每題自己的監聽負責。
- 其他用到投稿的地方（作答存摺、模擬考結果、錯題本、難題本、每日抽題）維持原本做法。

效果：逐題看完一份 80 題的試卷，讀取次數從 90／160／410 次降到約 10／29／89 次（分別是無投稿／20 則投稿／熱門卷）。

你會看到的差異：第一次打開討論區時，按讚數和回覆會稍晚一點出現。

### 7.5 作答紀錄與筆記：增量同步

檔案：`src/components/cloud-sync-provider.tsx`、新增的 `src/lib/cloud-sync-checkpoint.ts`、`firestore.rules`

做法：

- 每個帳號在每個瀏覽器記一份「同步檢查點」，存在 localStorage 的 `shaneweb:cloud-sync:<uid>`。裡面只有編號和時間，沒有作答或筆記內容：
  - 已確認存在雲端的作答紀錄編號，以及筆記版本；
  - 最後看到的伺服器同步時間（`syncedAt`）；
  - 雲端上本網站讀不懂的紀錄編號（例如較新版本程式寫的），用來核對筆數，以及上次重新讀它們的時間；
  - 最近 1,000 筆已確認從雲端刪除的作答紀錄編號：雲端刪除紀錄裡的，加上這個瀏覽器自己看到的。
- 每個帳號在雲端多一份**刪除紀錄** `users/{uid}/deletions/attempts`，記最近 1,000 筆被刪除的作答紀錄編號：
  - 刪除作答紀錄時，用一個交易同時刪掉紀錄、把編號加進刪除紀錄（一次最多 100 筆）。
  - 交易被規則拒絕時（規則還沒發布），改成像以前一樣直接刪除，只是這筆不會記進刪除紀錄。
  - 規則只允許本人讀寫，最多 1,000 筆，時間由伺服器蓋上，不能刪除整份紀錄。
- 冷啟動時先讀刪除紀錄：裡面有的紀錄從本機移除、永遠不上傳；雲端若還留著一份（舊版程式傳回去的），會再刪掉。
- 接著，只要本機資料仍涵蓋檢查點，就只讀「同步時間 ≥ 上次」的作答紀錄與筆記，再用 1 次 count 核對雲端筆數。別的裝置用新版刪除的紀錄已經寫在刪除紀錄裡，不會造成筆數對不上。
- 筆數對不上時才完整讀一次。雲端不見、但沒有被記為已刪除的紀錄，視為雲端遺失，重新上傳。
- 讀不懂的紀錄平常不重讀。頁面剛列入新的一筆時，下次載入會依編號重讀（每次查詢 30 筆），之後每天最多一次，看這一版是否讀得懂。
- 每份讀到的文件只轉換一次資料，紀錄多時載入比較省計算。
- 即時監聽也只看「這次載入之後」的變動，所以分頁在背景超過 30 分鐘再回來，只會重讀新增的部分。
- 開著的分頁另外監聽刪除紀錄：其他裝置刪除時，較舊的紀錄也會即時從畫面移除。
- 沒有檢查點（第一次在這個瀏覽器登入、清除過資料）或檢查點不成立時，照舊完整讀取，並建立檢查點。

安全措施：

- 從快取讀到的結果不會刪除任何東西，刪除紀錄也只採用伺服器的回應。
- 雲端不見、但沒有被記為已刪除的紀錄（例如在主控台誤刪、雲端資料遺失），一律**不刪本機**，改成重新上傳，跟改動前的行為一樣。不管一次不見幾筆都這樣處理，原本「超過 20 筆、而且超過四分之一」的門檻拿掉了。
- 已確認刪除的紀錄會記在檢查點裡。其他開著的分頁會立刻把它從畫面移除；就算被舊分頁存回本機，下次載入也會移除，不會再上傳。
- 雲端上讀不懂的紀錄另外記錄，不會導致每次都完整讀取。

效果：

- 每次冷啟動，作答紀錄與筆記的讀取從 A + N 次降到約 5 次：兩個增量查詢至少各 1 次、1 次 count，加上刪除紀錄的讀取與監聽各約 1 次。難題標記、偏好設定、作答進度的讀取照舊。
- 刪除作答紀錄：每次刪除（一次最多 100 筆）多 1 次讀取（交易讀刪除紀錄），每個開著的分頁（包括刪除的那個）再各收 1 次。
- 讀不懂的紀錄重讀時，每筆 1 次，每個查詢至少 1 次；沒有這類紀錄就不讀。
- 情境 (b) 的重度使用者：每天約 6,400 次降到約 520 次。情境 (b′) A≈1,000、一天重新整理 30 次的帳號：約 32,000 次降到約 260 次。刪除紀錄每次冷啟動多約 2 次，已算在裡面。

你會看到的差異：

- 在 A 裝置刪除的作答紀錄，B 裝置下次載入時會跟著消失，B 裝置上一直開著的分頁也會即時移除。改動前，B 裝置會把它重新上傳回雲端。
- 離線時刪除作答紀錄，雲端那份要等恢復連線才刪，這段期間會出現提示：「紀錄已從本機移除，恢復連線後會自動刪除雲端紀錄。」恢復連線時會馬上補刪；瀏覽器沒發現自己斷線（例如連上沒有網路的 Wi-Fi）或當日額度用完時，也會每隔一段時間自動再試（從 1 分鐘起、每次加倍、最長 30 分鐘；額度用完從 5 分鐘起）。改動前，離線刪除會默默排隊，不顯示這個提示。
- 過渡期的限制：
  - 還在跑舊版程式的分頁刪除的紀錄，以及新規則發布前刪除的紀錄，都不在刪除紀錄裡。其他裝置會把它們當成雲端遺失，重新上傳，跟改動前一樣。
  - 舊版分頁也可能把已刪除的紀錄傳回雲端，新版載入時會再刪掉。
  - 一台裝置若很久沒載入，期間帳號又刪了超過 1,000 筆，更早刪除的紀錄可能被它送回雲端。

沒有改的部分：難題標記、介面偏好、未完成作答進度（見第八節 N5）。

### 7.6 這次代你做的決定

- 公告統計維持現有的 Firestore 交易，只加上退避與多分頁協調。要不要改用 GA4 或 `increment`，留給你決定（第九節第 2 點）。
- 公告監聽遇到缺索引、規則沒部署這類錯誤就停止重新訂閱，等恢復連線或重新載入。代價是規則晚發布時，已開著的頁面要重新整理才收得到公告。
- 爬蟲的處理方式是不啟動 Firebase，而不是在 robots.txt 擋 `/exams/`，以保留 SEO。
- 跨裝置刪除改用雲端的刪除紀錄：各裝置載入時照著刪，開著的分頁即時刪，取代原本「重新上傳」的行為。
- 刪除紀錄只留最近 1,000 筆，用一份文件就裝得下，每次讀取只算 1 次。
- 刪除交易被規則拒絕時改用單純刪除，讓刪除在規則發布前也有效，只是不記進刪除紀錄。
- 雲端不見、但沒有被記為已刪除的紀錄，一律當作資料遺失：保留本機並重新上傳。原本「少掉超過 20 筆、且超過四分之一」的門檻拿掉了。
- 雲端上讀不懂的紀錄，每天最多重讀一次。
- 討論區打開過之後，切回題目分頁仍保留回覆與按讚的監聽，避免來回切換時重複讀取。
- 修改了 `firestore.rules`，只新增刪除紀錄 `users/{uid}/deletions/attempts` 的規則，所以這次**要先部署規則**（7.8）。
- 每日抽題的批次讀取（N1）先不做：`in` 查詢怎麼計費，官方沒有寫清楚，要先用 `?fsdebug=1` 量測。
- IndexedDB 持久快取（N7）先不做：iOS 和多分頁的風險比較高，而且上面幾項已經處理了主要成本。

### 7.8 上線後要注意

- **先部署規則，再 push**：`firebase deploy --only firestore:rules --project shaneweb`，到 Console 的 Rules 確認已發布後才 push。這次只新增刪除紀錄 `users/{uid}/deletions/attempts` 的規則，沒有新索引。

- 本機的 `node_modules` 補裝了 `@firebase/rules-unit-testing`。它早就列在 package.json，但一直沒安裝，所以 `tsc` 一直報錯。`package-lock.json` 沒有變動。

## 十二、考慮過但不建議的做法

- **在隱藏的分頁暫停監聽**：閒置的監聽不收費，重新連上反而至少收 1 次；超過 30 分鐘還要整批重讀。
- **另外手寫 `memoryLruGarbageCollector`**：SDK 12 的預設已經是它。
- **用 BroadcastChannel 自己做「主分頁」**：等於重做 N7 的 `persistentMultipleTabManager`。
- **公開資料做 Firestore bundles 或 ISR 內嵌投稿**：每次重建都要重讀投稿，回覆與按讚仍要即時監聽，效益不如 N6。
- **用 `count()` 或 `increment()` 算按讚數**：`count()` 不能即時監聽，每次都收費；計數器需要規則讀取，也會漂移，按讚數量又少。
- **改成計時輪詢**：每次輪詢都至少收 1 次，即時監聽只在有變動時收費。
- **App Check 擋爬蟲**：會增加 reCAPTCHA 負擔，Safari 與主畫面 App 也有風險。用 User-Agent 判斷就夠了。
- **robots.txt 擋 `/exams/`**：會抵銷 1.100 的 SEO 成果。
- **Firestore Lite SDK**：每份文件的計費相同，只是程式比較小。
- **把難題設定和介面設定合併成一份文件**：每次冷啟動只省 1 次。
